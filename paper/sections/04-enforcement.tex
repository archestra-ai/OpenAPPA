\section{Enforcement}\label{sec:enforcement}

\paragraph{Check 1---tool-requirement compatibility.}
The first check enforces standard sink-side information flow control (IFC) adequacy~\cite{sabelfeld2003language} against the prospective Label $c_\tau(L) = L \meet d_\tau$, where $d_\tau$ is the effective contribution of the call (\S\ref{sec:model}):
\begin{itemize}
  \item \textbf{Narrowing} is determined by comparing the prospective Label $c_\tau(L)$ against the current trajectory Label $L$ ($c_\tau(L) < L$);
  \item \textbf{Label requirements}---trust floor, audience inclusion ($\readers(c_\tau(L)) \supseteq \mathrm{recipients}(\mathrm{args})$, with placeholders resolved by parameter substitution), and audience cap---are evaluated against the prospective Label $c_\tau(L)$;
  \item \textbf{History requirements} (\texttt{prior} and \texttt{no\_prior}) are evaluated against the current committed-effect projection $\mathcal{E}(\ell)$ before dispatch; and
  \item \textbf{Hard gates} remain per-call requirements.
\end{itemize}
Evaluating release requirements against $c_\tau(L)$ ensures safety for combined operations (e.g., \texttt{search\_and\_share}), where data acquired by a call contributes to the Label checking that call's release conditions. This mechanism adapts noninterference principles~\cite{goguen1982security} to tool invocation.

\paragraph{Check 2---state acquisition.}
We order $S$ by restrictiveness, where $s' \le s$ if and only if the readers of $s'$ are a subset of those in $s$ and the trust level of $s'$ is less than or equal to that of $s$. Because every label update is a meet operation, trajectory state monotonically descends or remains fixed along both dimensions. The checker enforces least privilege at trajectory granularity~\cite{saltzer1975protection} prospectively:
\begin{enumerate}
  \item \textbf{Prospective evaluation:} Before dispatch, the engine computes the prospective Label resulting if the call's output were admitted. For an ordinary raw output this is $s_{\mathrm{prosp}} = \fold(s, \texttt{delta(call)})$; an output transformation is checked using the admitted derivation Label.
  \item \textbf{Narrowing block:} If a call restricts trajectory permissions ($s_{\mathrm{prosp}} < s$), the engine blocks execution before dispatch.
  \item \textbf{In-session acceptance:} Clearing an acquisition block requires an explicit \texttt{Accept} step from the agent.
  \item \textbf{Atomic plan composition:} If a tool call both restricts permissions and has unmet requirements, the engine combines the agent's \texttt{Accept} step and any necessary \texttt{Authorize} approvals into a single atomic remedy plan.
  \item \textbf{Same-trajectory dispatch:} Successful remedy execution atomically records narrowing acceptance, required rulings, and opened dispatch in the trajectory without changing the Label. If a result value is admitted, its Label enters the fold; otherwise, the Label is unchanged.
\end{enumerate}

Trajectory branching is deliberately excluded from the mechanisms that clear an acquisition block. Because a child trajectory is seeded from the parent's current label state $s_{\mathrm{parent}}$, it inherits the same initial restrictions; context branching serves as an engine-level orchestration option to isolate execution under inherited labels (\S\ref{sec:branching}) rather than clearing parent restrictions. Clearing an acquisition block within any active trajectory strictly requires explicit agent acceptance. The two verification steps remain decoupled: an external policy ruling cannot accept state narrowing on behalf of the agent, and agent acceptance cannot satisfy an unmet tool requirement.
Because release-side requirements (trust floor and audience cover) are monotone in the trajectory label $s$, state descent can only shrink the set of tool requests satisfiable without explicit rulings. Conversely, upper context bounds (such as source bounds $\subseteq C$) are antimonotone: narrowing permissions can cause a previously failing upper bound to become satisfied, which excludes them from the monotone scope of Call-Scoped Release (Theorem~\ref{thm:release}).

\paragraph{Label monotonicity.}
In the primary model, tool deltas only narrow access, never elevating trust or expanding readership. A single tool call, such as \texttt{search\_and\_share}, may simultaneously narrow permissions and have an unmet tool requirement. In this case, an atomic remedy plan combines an \texttt{Accept} step for state narrowing with an \texttt{Authorize} step for the unmet requirement. Tools that grant access, such as \texttt{share\_doc(doc, outsider)}, are modeled as a fetch operation composed with an access-granting action, allowing each operation to be evaluated independently.

\begin{theorem}[Remedy completeness for the modeled subset]\label{thm:remedy}
Given the registered configuration and finite planner state $(L, \mathrm{supp}\,\mathcal{E}(\ell))$, and restricting to runs in which a pending-cast success checkpoint and its value finalization are observationally atomic with respect to subsequent policy checks, if the planner returns neither an executable plan (\texttt{Authorize}/\allowbreak\texttt{Accept}) nor a curative \texttt{Redispatch} recommendation, the blocked call is unreachable within the planner's modeled transition system.
\end{theorem}
This empty-result verdict serves as a proof of unreachability within the transition system. The planner enumerates atomic \texttt{Authorize}/\allowbreak\texttt{Accept} plans and curative \texttt{Redispatch} sequences, while advisory \texttt{Branch} recommendations provide engine-level guidance for context isolation without altering transition reachability. Proof in Appendix~\ref{app:proofs}.

\paragraph{Remedy-plan delivery.}
The planner distinguishes atomic executable plans from prose or advisory recommendations. Executable plans---\texttt{Authorize} (issuing policy rulings), \texttt{Accept} (accepting state narrowing), or single-call compositions combining both---are executable objects exposed through a static tool, \nolinkurl{execute_remedy_plan(plan_id)}, initialized at run start to avoid invalidating prompt caches~\cite{kwon2023efficient}. The plan identifier, tool dispatch, and associated policy rulings are logged upon execution. Unmet hard gates use the same interface: a hard gate is treated as a failed predicate requiring an atomic ruling.

By contrast, \texttt{Redispatch} recommendations are non-atomic: they propose two or more separately checked calls (e.g., registered tools whose successful effects satisfy a failed \texttt{prior(k)} requirement or whose restrictive deltas cure an audience cap). Redispatched calls are ordinary tool calls checked and executed independently, after which the original target call must be reproposed and rechecked. Advisory \texttt{Branch} recommendations suggest context isolation without directly satisfying unmet tool requirements.
