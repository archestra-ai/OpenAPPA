\section{Enforcement: The Two Checks}\label{sec:enforcement}

\paragraph{Check 1---tool-requirement compatibility.}
The first check enforces standard sink-side information flow control (IFC) adequacy~\cite{sabelfeld2003language}: the trust level of the trajectory must satisfy the tool's required trust floor, and the reader set must cover all intended recipients, $\readers(\fold) \supseteq \mathrm{recipients}(\mathrm{args})$, with placeholders resolved by direct substitution of call parameters. This mechanism adapts standard noninterference principles to tool invocation.

\paragraph{Check 2---state acquisition.}
We order $S$ by restrictiveness, where $s' \le s$ if and only if the readers of $s'$ are a subset of those in $s$ and the trust level of $s'$ is less than or equal to that of $s$. Because every label update is a meet operation, trajectory state monotonically descends or remains fixed along both dimensions. The checker enforces the principle of least privilege at trajectory granularity~\cite{saltzer1975protection} through a prospective evaluation protocol:
\begin{enumerate}
  \item \textbf{Prospective evaluation:} Before dispatch, the engine computes the prospective Label that would result if the call's output value were admitted. For an ordinary raw output this is $s_{\mathrm{prosp}} = \fold(s, \texttt{delta(call)})$; a registered output transformation is checked using the Label of the derivation that would actually be admitted.
  \item \textbf{Narrowing block:} If the call strictly restricts trajectory permissions ($s_{\mathrm{prosp}} < s$), the engine blocks execution prior to dispatch.
  \item \textbf{In-session acceptance:} Clearing the acquisition block in the active trajectory requires an explicit \texttt{Accept} step from the agent.
  \item \textbf{Atomic plan composition:} If a tool call both restricts permissions and has unmet requirements, the engine combines the agent's \texttt{Accept} step and any necessary \texttt{Authorize} approvals into a single atomic remedy plan.
  \item \textbf{Same-trajectory dispatch:} Successful remedy execution atomically records the narrowing acceptance, any required rulings, and the opened dispatch in the same trajectory. None of these actions changes the current Label. If a result value is subsequently admitted, its validated Label enters the trajectory fold; if no value is admitted, the trajectory Label remains unchanged.
\end{enumerate}

Trajectory forking is deliberately excluded from the mechanisms that clear an acquisition block. Because a child trajectory is seeded from the parent's current label state $s_{\mathrm{parent}}$, it inherits the same initial restrictions; context branching serves as a host-level orchestration option to isolate execution under inherited labels (\S\ref{sec:branching}) rather than clearing parent restrictions. Clearing an acquisition block within any active trajectory strictly requires explicit agent acceptance. The two verification steps remain decoupled: an external policy ruling cannot accept state narrowing on behalf of the agent, and agent acceptance cannot satisfy an unmet tool requirement.

The release frontier characterizes system-level behavior rather than individual checked objects. Because tool requirements are monotone in $s$, state descent can only reduce the set of requests satisfiable without external rulings. Conversely, upper context bounds ($\subseteq$) work in reverse: narrowing permissions can actually satisfy a previously failing bound, which excludes them from the scope of the release frontier theorem.

\paragraph{Label monotonicity.}
In the primary model, tool deltas only restrict access and never elevate trust or expand readership. A single tool call, such as \texttt{search\_and\_share}, may simultaneously narrow permissions and have an unmet tool requirement. In this case, an atomic remedy plan combines an \texttt{Accept} step for state narrowing with an \texttt{Authorize} step for the unmet requirement. Tools that grant access, such as \texttt{share\_doc(doc, outsider)}, are modeled as a fetch operation composed with an access-granting action, allowing each operation to be evaluated independently.

\paragraph{Evaluation timing.}
Label requirements are evaluated against the prospective state that admission of the tool result would produce. This prevents race conditions where a tool call, such as \texttt{search\_and\_share} configured with \texttt{requires: audience=public} and \texttt{delta: audience=internal}, might satisfy requirements under the current state despite committing internal data upon execution. By contrast, history predicates evaluate the log in its current pre-state, ensuring that a tool call's \texttt{emits} sequence cannot satisfy its own prerequisites.

Source bounds ($\subseteq$) evaluate against the same prospective Label as other Label requirements. A call can therefore satisfy a sensitivity cap simply because its own output narrows trajectory permissions. The implemented system does not additionally test the trajectory's pre-state. External communication channels that display messages to fixed readers independently of label state operations are outside the scope of this model, which governs agentic trajectories rather than arbitrary channel IFC. Memory eviction mechanisms are reserved for the permissive extension.

\begin{theorem}[Implemented Remedy completeness]\label{thm:remedy}
Given the registered configuration and the finite system state $(L, \mathrm{supp}\,\mathcal{E}(\ell))$, if the planner returns neither an executable plan (\texttt{Authorize}/\texttt{Accept}) nor a curative \texttt{Redispatch} recommendation, the blocked call is unreachable within the implemented transition system.
\end{theorem}
This empty-result verdict serves as a proof of unreachability within the transition system. The planner enumerates atomic \texttt{Authorize}/\texttt{Accept} plans and curative \texttt{Redispatch} sequences, while advisory \texttt{Fork} recommendations provide host-level guidance for context isolation without altering transition reachability. Proof and formal scope bounds in Appendix~\ref{app:proofs}.

\paragraph{Remedy-plan delivery.}
The planner distinguishes atomic executable plans from prose or advisory recommendations. Executable plans---\texttt{Authorize} (issuing policy rulings), \texttt{Accept} (accepting state narrowing), or single-call compositions combining both---are executable objects exposed through a static tool, \texttt{execute\_remedy\_plan(plan\_id)}, initialized at run start to avoid invalidating prompt caches~\cite{kwon2023efficient}. The plan identifier, tool dispatch, and associated policy rulings are logged upon execution. Unmet attention requirements use the same interface: an attention demand is treated as a failed predicate whose remediation is an atomic ruling.

By contrast, \texttt{Redispatch} recommendations are non-atomic: they propose two or more separately checked calls (e.g., registered tools whose successful effects satisfy a failed \texttt{prior(k)} requirement or whose restrictive deltas cure an audience cap). Redispatched calls are ordinary tool calls that are checked and executed independently, after which the original target call must be reproposed and rechecked. Advisory \texttt{Fork} recommendations suggest context isolation to the host engine without directly satisfying unmet tool requirements.
