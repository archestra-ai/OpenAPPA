\section{Atomic Rulings and Robust Declassification}\label{sec:rulings}

\paragraph{One judgment and one dispatch rule.}
Every judgment follows a single canonical form: authority $A$ authorizes engine-rendered call $C$. No separate grant objects or permission types are configured or transmitted over the wire; the public system vocabulary consists exclusively of mandates, rulings, and log records. A call is dispatched if and only if rulings cover all failed or demanded predicates, each issuing authority's mandate authorizes the admitted exception, and all rulings reference the identical rendered call and are consumed atomically. While a single ruling typically suffices, multi-party authorization policies (such as two-person control~\cite{}) require collecting multiple rulings. A ruling permits dispatch despite an unsatisfied predicate but never modifies the execution trajectory directly, which evolves solely through the admitted call's own \texttt{delta} and \texttt{emits} fields. Furthermore, no ruling can bypass or substitute for the agent's deliberateness gate required for narrowing (\S\ref{sec:enforcement}).

\paragraph{Atomic plan execution.}
For a plan requiring authorization on a suspended execution run, a single indivisible step renders the call, presents provenance information (excluding sensitive payload bytes) to the authority, and dispatches upon approval. The plan identifier, ruling, and dispatch event are recorded atomically in the execution log. Acceptance plans are inherently atomic, as accepting a plan and dispatching its call require no external authority round-trip. Because approval and dispatch coincide, traditional multi-stage grant lifecycles (such as issuing, binding, and consuming permissions)~\cite{} collapse into an atomic operation. Consequently, intermediate state cannot be intercepted or modified: the ruling explicitly binds to the rendered call to prevent call substitution, authorization applies strictly to a single dispatch to prevent replay attacks~\cite{}, and the event is fully reconstructible from the log. In linear logic terms, the consumable capability is consumed simultaneously with its creation \cite{wadler1990linear}.

\paragraph{Call-scoped release.}
A ruling applies strictly to a single dispatch without altering the trajectory state (the accumulated security label). The ruling and resulting external event record the authorized release, while the security label continues to accurately reflect the underlying classification of the data. This scope isolation is critical in taint-isolated execution branches: an authorized exception or exit cannot ambiently relax labels for either child or parent contexts during subsequent attacker-influenced calls. The trajectory label itself is never persistently widened. Although an epoch-wide permissive delta is algebraically feasible, it is intentionally excluded; dynamic branching satisfies this operational requirement (\S\ref{sec:branching}), subject to the tradeoffs outlined in \S\ref{sec:limitations}.

\paragraph{Mandate typology.}
Authority is bound to declarations rather than dynamic runtime objects, with each mandate specifying the permission scope it governs. A cover mandate permits trust-level deficits up to a specified rank or audience restrictions up to a defined ceiling without altering security labels. A named waiver explicitly designates the \texttt{no\_prior} event types it is permitted to exempt. An attends mandate specifies attention markers whose requirements a ruling satisfies, allowing tools and authorities to interact via decoupling markers rather than direct references. A single ruling may simultaneously address a predicate deficit and an attention demand for a given call, but it can never bypass the narrowing-acceptance gate; multi-party review employs distinct attention markers checked by separate authorities. Capability acquisition mechanisms are deliberately omitted, as accepting state descent represents an unconstrained agent plan rather than an elevated permission.

Scope operates as a distinct classification dimension routed strictly via \texttt{tags}; security parameters such as trust level, target audience, and side effects serve as validation criteria rather than routing keys. Security soundness remains independent of tags, because even a misrouted authorization check cannot exceed the issuing authority's mandate and must still evaluate the exact rendered call. Only policy completeness relies on correct tag routing.

\paragraph{Response-sink rule.}
No end-user ruling can authorize a predicate for a response-sink release, irrespective of the user's other mandate privileges. Because approval requests for such releases would travel through the very channel being released, in-band self-approval cannot provide structural security guarantees~\cite{}.

\paragraph{Canonical rulings and robust release.}
Authorities evaluate the engine's canonical representation of a tool call. This eliminates semantic evasion vectors where a compromised model might request an action under misleading phrasing (such as requesting to email a compliance archive while omitting a destination address injected by an attacker). Remedy-set soundness provides resilience against plan selection: because every plan option generated by the engine is independently sound, a compromised planner cannot cause a security violation merely by choosing among them. Under established declassification models, sanitization regulates *what* information is released, whereas rulings govern *who* is authorized to permit the release \cite{sabelfeld2009declassification}. When an agent processes attacker-controlled input, untrusted data may influence which candidate requests the agent formulates, but it cannot dictate which releases are authorized. Authorization strictly requires sink compatibility or a valid, mandate-bounded ruling over the exact rendered call. This mechanism establishes an agent-oriented model of robust declassification \cite{zdancewic2001robust}.

\paragraph{Sanitizers.}
Registered sanitizers transform values according to authorized state transitions; they do not modify execution trajectories, as retrospective sanitization cannot erase data already incorporated into model context~\cite{}. When applied at the output boundary, a transformed derivative is released while the raw output remains confined, preserving context security but requiring a restricted execution environment. When applied at the input boundary, the derived value replaces the raw argument in the canonical tool call rendered by the engine, allowing the harness to transmit redacted payload bytes. While input-side sanitization protects external sinks across all deployment environments, it cannot retroactively undo prior context exposure. Sink validation checks rely on the declared label of the sanitized derivative rather than the original raw argument; trajectory labels remain unmodified, and sanitizer invocations are recorded in the log.

Sanitizer transformations adjust the audience scope exclusively; sanitization never elevates the trust level of data. While deterministic transformations can restrict who may read derivative outputs, asserting that output has become trusted requires an explicit ruling or type cast. The sole structural exception to this rule is quarantine-exit attestation (\S\ref{sec:branching}). Mandates authorize specific transformation functions rather than arbitrary information types: for instance, a \texttt{remove\_pii} transformation might be sound for processing CRM support tickets yet unsafe if applied to a dataset composed entirely of PII. Finer-grained information-type scoping remains future work, and sanitizer registration trusts the transformer logic directly rather than verifying output values at runtime. Type casts represent an additional non-grant mechanism for resolving unknown security labels, operating either via constant values or resolver functions up to a declared target ceiling.

\paragraph{Single-command privilege elevation.}
A ruling provides transient privilege elevation strictly for a single tool call, leaving no ambient permissions active afterward~\cite{}.
