\section{Branching for Taint Confinement}\label{sec:branching}

\paragraph{Observation model.}
Once data enters an LLM context, subsequent sanitization cannot retroactively remove that information from the model's trajectory~\cite{caiGhostAgentRedefining2026}; modifying its security label would incorrectly represent its state. \appa{} never removes taint from an already exposed trajectory; instead, it avoids parent context degradation by confining restrictive descents to disposable child branches. The long-lived parent process pauses prior to a restrictive data acquisition, delegating the operation to a temporary child context. By confining label descent to the child branch, \appa{} prevents taint accumulation in the primary parent process, without asserting that the child process or source data is untainted.

\paragraph{Deployment requirement.}
Branching requires an execution environment capable of isolating context trajectories (e.g., an application harness or proxy gateway). While baseline label enforcement (\S\ref{sec:enforcement}) operates in standard gateways, features such as fork-before-read and output sanitization rely on runtime context confinement.

\subsection{Intercept before acquisition}
For a proposed call $t$, the runtime evaluates the prospective state by folding $\mathit{delta}(t)$ into the parent label $L_p$. If this update strictly reduces label permissions (i.e., causes a descent), the enforcement layer suspends $t$ prior to dispatch and presents a \texttt{fork} plan alongside options for acceptance or refusal. The plan specifies the initial call and defines the permitted structure of the child's eventual exit, rather than granting unrestricted execution.

\subsection{Fork by inheritance}
The child process inherits a copy of the parent's context and initializes its label from the parent's state at the fork point, setting $L_c := L_p^{\mathrm{fork}}$. Assigning an unconstrained initial label to the child would bypass the security controls of inherited context data—for instance, allowing internal context to be released to a public output. The \texttt{fork} boundary also invalidates pending rulings and plan executions, as these records are bound to specific invocations in the parent context and cannot be transferred to a child.

\subsection{Descend locally}
The suspended call is dispatched within the child context, where all subsequent actions are enforced against the evolving child label $L_c$. Updates to $L_c$ affect only the child label and never update $L_p$. The parent process may pause or proceed concurrently, but it remains isolated from child messages and tool outputs until an explicit exit occurs. This isolation guarantees the pre-merge properties of Proposition~\ref{prop:preservation}, regardless of the child's internal behavior.

\subsection{Exit explicitly}
An execution branch yields one of three outcomes:
\begin{enumerate}
  \item an \texttt{abandon} signal;
  \item the return of a standard labeled value; or
  \item the application of a registered sanitizer or verified exit transformation that produces a derived value.
\end{enumerate}
In all cases, APPA validates the actual result label prior to committing the merge. If the raw result would restrict permissions, it triggers the acquisition check in the parent context. The parent may explicitly accept the label reduction or reject the \texttt{merge}; however, accepting lower permissions does not achieve taint confinement. A declared exit bound can be verified prior to execution to enable planning, though the actual result label remains authoritative.

\begin{theorem}[Branch taint confinement]\label{thm:branch}
Let a parent fork at $L_p^{\mathrm{fork}}$, and let the child execute any admitted trace. If the branch is abandoned, child execution does not change the parent's independently evolved label. If the child returns $v$, merging yields
\[
  L_p' = L_p \wedge \mathit{label}(v).
\]
Hence no child can widen or silently degrade its parent's label, and an exit satisfying $L_p \le \mathit{label}(v)$ preserves the parent label exactly.
\end{theorem}

\paragraph{History is shared, not merged.}
The parent and child process append to a single, real-time serialized event log. Any egress operation or side effect executed by a child remains recorded in external history even if the child branch is subsequently abandoned; context isolation cannot undo these actions nor clear them from future \texttt{no\_prior(egress)} policy checks~\cite{wangAgentTracesTrust2026}. Forking and merging function as governance operations. A policy ruling granted to a child is consumed during its execution and does not grant authorization to the parent. Each branch terminates via return, failure, or abandonment, requiring no log reconciliation because physical event history is never branched.

\paragraph{Sanitized branch exits.}
Following the Dual-LLM and CaMeL architectures~\cite{willison2023dual,camel2025}, sanitized branch exits pair a predeclared \texttt{submit\_result} schema with registered transformation functions. Schema validation alone never relaxes label restrictions, as structural compliance does not guarantee safe provenance~\cite{sabelfeld2003language}. Maintaining a parent process's trust level may require a verified transformation assertion~\cite{zdancewic2001robust}—for example, asserting that ``the returned integer represents a version number from the specified source and contains no unparsed text''—rather than simple parsing. Registering such a transformation incorporates its claim into the trusted computing base; this transformation assertion represents APPA's sole exception for structured label promotion without an explicit policy ruling.

\paragraph{Compiled fork plans.}
A multi-step execution branch can compile into a single synthesized invocation with a declared result-label bound that is validated against the parent. The plan body executes entirely within the confining environment; each intermediate step is checked against the evolving child state without exposing intermediate data to the parent. If an operation within the plan requires a policy ruling, the authorizing component evaluates the ordered steps as part of the rendered request object. Execution proceeds in two phases: APPA first verifies the declared outer bound, then validates the actual result label prior to the merge. If validation fails, the returned value is discarded, though recorded side effects persist in the event log. The effective state delta applied during merge reflects only the returned value, rather than the cumulative internal deltas of the child steps.

\paragraph{Worked pattern.}
Consider a scenario where a high-trust parent process requires an invoice total from an untrusted internal CRM record. Inspecting the record directly within the parent context would restrict the security label for all subsequent operations. APPA forks the execution prior to issuing \texttt{read\_crm}, computes the required total within the child context, and restricts output via \texttt{submit\_result(integer)} using a registered output sanitizer for invoice totals. The parent receives the resulting integer while preserving its original label, whereas the raw record and any untrusted text remain confined to the child branch prior to its termination.
